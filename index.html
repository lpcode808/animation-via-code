Animation via code

Short explainer videos made by asking an AI coding agent to write code that draws every frame.

Notes from a few dozen short pieces, most between 15 seconds and 3 minutes long, on what worked and what broke. Each note says how sure we are of it. There are also prompts, a small template, and three demos with their source.

01WHY

Why code instead of a video model

A video model

Quick, and often good-looking. Hard to correct, though: asking for a fix usually gets you a different clip.

Code

Every shape, number and caption is exact and can be changed. If a reviewer says an arrow points the wrong way, you change one line and render again.

For teaching, that means a caption that says "3 + 4 = 7" can be checked against the diagram. The trade-off is that you, or the agent, have to describe things precisely, and a render takes minutes.

Each frame is a pure function of time. renderAt(t) draws the same picture for the same t, no matter what came before.

Because of this, frames can be rendered in parallel, one second can be rendered again on its own, and the preview matches the final file. The ball at the top of the page works the same way: wherever you drag the slider, the frame is drawn from t alone.

  1. PromptTopic, audience, style, length.
  2. Scene codeThe agent writes renderAt(t).
  3. FramesA headless browser captures each one, 30 or 60 fps.
  4. Soundnumpy writes music and effects as raw samples.
  5. MP4ffmpeg joins frames and audio.
  6. ReviewContact sheets, a fresh reviewer, fix, re-render.

This is the most common route. Pieces here also used SVG rasterizers, skia-python with no browser (how the demos were made), Manim, Remotion and headless Blender. Pick for the subject.

What reviewing them caught

  • Bouncing ball. The caption covered the ball once it came to rest, and "It speeds up as it falls" appeared after the first bounce. The floor moved up, the beats were retimed to the physics, and a check now pins them together.
  • Pythagorean proof. The first draft placed two triangles wrong. The geometry checks failed before any frame rendered.
  • Water cycle. Three fade windows didn't wrap round the loop's end, so the seam check failed until they did. The first caption was also too wide, and rain fell through the mountain.
04START

Where to start

  1. 1

    Try it with a prompt

    Paste the prompt card into a coding agent that has a shell and ffmpeg, with your topic filled in. Expect 10 to 20 minutes for a 20 to 30 second clip.

  2. 2

    Watch and read the demos

    Three short videos with their full source, each with a check that runs before any frame renders.

  3. 3

    Run the template

    A 6-second browser version of the bouncing ball in about 200 lines: one HTML scene, a render script, a synth soundtrack and a mux step. Its browser render hasn't been run yet, so expect to fix small things.

  4. 4

    Read the guide before your second video

    Filed by stage, from planning to companion pages. Each stage has its lessons, then the bugs that cost time there.

  5. 5

    Try a longer prompt

    Demo prompts, a review pass, a long one-shot film prompt, and a brief for turning a video of yourself talking into a motion-graphics edit.

If you're an agent asked to use this repo

Don't read the whole guide up front. Read the prompt card and stage 1, and show your user a beat list before drawing. Copy the demo closest in length to demos/<topic>.py, keeping its DURATION, draw, checks and soundtrack, check a few stills, and run python3 build.py <topic>. Review as stage 6 says. Done means the MP4, its contact sheet, checks that pass, a list of what you guessed at, and a note that no person has watched it yet.

05PROMPTS

Prompts

Start with the short card. The longer prompts are for later pieces.

The prompt card
Make a [15–30 second] video about [topic] for [who it's for].
[Style: e.g. flat shapes, chalkboard, blueprint].
[Attach a PDF or handout, or say "use what you know"].
Captions, no narration. Go all out.
Done means [a new viewer can explain the idea after one watch].

Fill in the brackets and paste it into a coding agent that has a shell and ffmpeg. Captions-only pieces were consistently the fastest; narration made every piece take much longer.

  • Prompt cardThe short prompt on the left, with why each line is there and what to add on a second try.
  • Demo promptsFive prompts for showing the method live, each picked to show something different.
  • One-shot film prompt (single HTML file)A long prompt for a 60 to 120 second film in one self-contained HTML file: picture, music and recording mode together.
  • Review pass promptRun it in a fresh agent session with the contact sheets and caption list. The single biggest quality lever.
  • Starter-kit promptWhen a folder of helpers carries the rules, the prompt itself can be very short.

01 Plan the piece 14 lessons · 1 pitfall

Decide what the video teaches, in what order and how long each idea holds, before any code exists. Most bad videos were bad plans drawn well.

  • confirmedPlan before you draw. Spend the first couple of minutes on a beat list: what's on screen, what the caption says, and how long it holds.
  • confirmedShort prompts work if they cover five things. Length and purpose, audience, one or two taste constraints (more than three start to conflict), source material, and permission to go big ("go all out").
  • confirmedWrite a "done means" line. For example: "done means a new person watching can understand the concept." It gives both you and the agent a test for every review.
  • confirmedExpect the agent to flag conflicts. If the length and the content can't both be true (the song runs 45 s, you asked for 30), a good agent says so before coding and picks a stated default.
  • confirmedStoryboard at sketch fidelity first. A rough shot list or pencil-style frames are cheap to fix.
  • tentativeFive to seven new ideas a minute. A first-time viewer absorbs about that many ideas in 60 seconds.
  • confirmedPick an order for the idea, not the topic. A beat order that worked again and again: an everyday analogy, then a diagram, then a worked example, then the idea in plain English, and only then the technical name or formula.
  • confirmedShow the skill, don't describe it. "Watch the gear mesh" beats "gears transfer torque".
  • tentativeBefore and after. A quick "without this / with this" contrast holds attention better than a straight walkthrough, especially at the start.
  • tentativeCompress the repetitive middle. When a process repeats (printing layers, sanding, a loop of code), show one cycle properly, then a short montage, then the result.
  • confirmedEnd on something usable. Close on a recap line, a question to try, or the one rule to remember, not on a logo or a fade.
  • tentativeUse the source's own words and structure. Keep the source's verbs, turn the author's own metaphors into the visuals, and when a document's prose and its tables disagree, follow the tables.
  • confirmedGive each video its own identity. After a run of pieces, the same plucks, pads, chimes and card layouts crept into everything.
  • contestedTime box. One target was 15 minutes from prompt to MP4 for a 15 to 30 second clip: plan by minute 2, a contact sheet by minute 7, review by minute 10.

Pitfalls that cost time here

  • Can't download a reference image or asset

02 Pick a renderer 9 lessons · 8 pitfalls

Choose what draws the frames for this subject, then get it working once. The rule that matters in every renderer is the same: each frame is a pure function of time (stage 3).

  • confirmedThere is more than one good renderer. Pieces in this collection used, among others: Canvas 2D in a headless browser; SVG strings rasterized with resvg; skia-python; a numpy "shader" for pixel effects; Manim for math scenes (rendered as parallel scenes); Remotion; DOM and SVG animated with a paused animation library and stepped through DevTools; three.js in software WebGL; and real Blender (installed from pip, Cycles on CPU) for a 12-second section at 720p and low samples.
  • confirmedCanvas 2D is the default renderer. It's fast, predictable and the agent knows it well.
  • tentativePython is fine too. The demos here use skia-python with no browser at all, at roughly 30 to 50 frames per second per worker for simple 1080p scenes.
  • confirmedReal 3D is expensive without a GPU. three.js in software rendering ran about one second per frame; one 3D piece (a 3D printer) took over 100 minutes to render.
  • confirmedSoftware WebGL needs flags. With no GPU, launch Chromium with --use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader for three.js or WebGL scenes.
  • confirmedHand-drawn brush looks are slow. Brush libraries without a GPU crawl.
  • tentativeFrame rate follows style. 12 fps drawn "on twos" and played at 24 reads as hand-drawn; 30 for motion graphics; 60 only when fine timing (fingers on keys) matters.
  • tentativeA framework may save the setup time. Left alone, the agent rebuilds the seek-and-screenshot harness from scratch each time, which costs 20 to 40 minutes.
  • tentativePages you can't seek can still be recorded. For timer-driven pages like slide decks, Chrome's DevTools screencast (Page.startScreencast) works where Playwright's video recording needs its own ffmpeg.

Pitfalls that cost time here

  • skia-python fails to import with a missing libEGL.so.1
  • CDN fonts don't load in the sandbox
  • Missing glyphs show as boxes
  • Code font turns -> or === into one glyph
  • An animated SVG group jumps to the top-left corner
  • A shape grows fake notches where parts overlap
  • A </script> inside a template literal ends the page's script
  • A model's weights won't download

03 Build the scene on one clock 9 lessons · 4 pitfalls

Write one timeline, and draw every frame from it. Picture, captions, narration and sound all read the same clock, so changing one beat moves everything with it.

  • confirmedOne clock for everything. Write a single timeline file (a table of beats with start and end times) and drive the picture, captions and sound from it.
  • confirmedFrames are a pure function of time. Write renderAt(t) so it draws the same frame for the same t, whatever came before.
  • tentativeNarrate what's on screen. When there is a voice, have it say the on-screen text word for word, space new terms about half a second apart, and define each term before using it.
  • tentativeNarration is optional and expensive in time. A local text-to-speech model plus a speech-to-text check (to confirm the words came out right) worked, but it pushed pieces well past a 15-minute box.
  • tentativeAdd time at the front without retiming everything. Keep the old timeline as "old time" (u = t - shift), draw the new intro in new time, and shift the sound cue list by the same amount.
  • tentativeRevisions without full re-renders. When an edit only changes a few seconds, remap the clock so unchanged frames are reused from the last render.
  • tentativeFor a loop, compare the last frame with the first. Make everything a function of the loop's phase, make anything that repeats inside the loop repeat a whole number of times, and let any soft on/off window wrap past the end.
  • tentativeReal footage: time comes from the words. When you edit a recording of someone talking, transcribe it with word timings ([word, start, end]) and hang every caption, graphic and sound cue on those times.
  • tentativeReal footage: use every source frame once, in order. Lay the footage out with keyframes (position, size, corner radius of the video card over time) and assert that each source frame appears exactly once and in order, so nothing is cut or doubled by accident.

Pitfalls that cost time here

  • Text "pops" in at full opacity for one frame
  • A fade-in plays twice or skips
  • Same seed, different frame
  • The camera is on the wrong side

04 Sound and mix 11 lessons · 2 pitfalls

Write the music and effects as code too, place them from the picture's own events, and measure the mix in the file you deliver.

  • confirmedSynthesize what you can. Most music and effects were written as raw samples with numpy: no sample libraries, no licensing questions.
  • confirmedLet the picture tell the sound where to go. Scenes call something like cue(scene, u, "whoosh") while rendering; the renderer writes those to cues.json; the audio script places each sound on its exact frame.
  • confirmedMusic on a bar grid. Pick a tempo so bars land on round seconds (120 bpm: one bar is 2 s) and line scene changes up with bar lines.
  • confirmedGive effects their own bus. Duck the music about 6 dB under effects.
  • confirmedMeasure peaks after encoding. AAC encoding raised true peaks by 4 to 5 dB in several pieces.
  • confirmedSeed every random choice, one stream per purpose. Use a seeded generator (mulberry32(hash(seed, n))).
  • tentativePin levels in tests. If you keep a library of instruments, test each part's loudness against the whole mix (for example ±0.5 LU).
  • tentativeSilence can be a beat. Cutting the music for under a second where something is supposed to happen and doesn't (a timer that never rings) made the point better than any sound.
  • confirmedLicensed music goes in last. If you'll use a real track, have the agent leave the music bed silent and add it in your editor.
  • confirmedThe agent can't hear. Every report should say whether a human has listened.
  • tentativeA real voice comes first. When the video has a recorded voice, high-pass it and compress it gently, duck the music under the words, and keep effects light.

Pitfalls that cost time here

  • A pad or choir throbs
  • Clicks at note ends

05 Render at scale 6 lessons · 6 pitfalls

Turn the scene into thousands of frames and one MP4 without babysitting it.

  • confirmedHeadless browser, many workers. Load the scene in headless Chromium with Playwright, call renderAt(t) for each frame, and save it as JPEG (screenshot, or read the canvas directly with toDataURL).
  • confirmedWait for a ready flag. Have the page set something like window.__ready = true after fonts load and any pre-rendering finishes, and have the capture script wait for it.
  • confirmedWrite numbered frames so the run can resume. 00000.jpg, 00001.jpg… A crashed render picks up where it stopped, and a bad range can be deleted and re-rendered: patch, don't restart.
  • confirmedRun it detached. Long renders die when the agent's shell is recycled.
  • confirmedEncode for everywhere. H.264, yuv420p, +faststart.
  • tentativeLocal hardware changes the rules. Everything here was tuned in a cloud sandbox (about 2 cores, no GPU, a network allowlist).

Pitfalls that cost time here

  • The first frames use the wrong font
  • A long render dies when the session goes idle
  • pkill render killed the agent's own shell, or pgrep found itself
  • ESM scripts can't find a globally installed package
  • A 20-second render came out 6 seconds long
  • Scripts lost their execute bit

06 Check it's right, then review 13 lessons · 3 pitfalls

Check the content first, then the frames, then ask someone who wasn't there.

  • confirmedA fresh reviewer is the biggest lever. After the first full render, start a new agent with no context, give it the video's contact sheets and caption list, and ask it to play two roles: someone seeing this for the first time, and a teacher of the subject.
  • confirmedModel the process, not its picture. If the subject is a machine or procedure, simulate what it actually does and let the animation show the result.
  • confirmedMake on-screen numbers live computations. Compute counts, measurements and totals in the page, and assert them against a source the subject already has (a measurement, a dataset).
  • tentativeWhen the subject is code, show the code that runs. Store it as a string, display that string, and run it to drive the picture and sound.
  • confirmedDon't let a caption claim something you didn't compute. "Where all three views agree, the object is" is only honest if the piece actually carves the object from the views.
  • confirmedCheck what a formula draws before captioning it. Captions written from notes, not from the render, described patterns that didn't appear.
  • confirmedAsk the agent to list its guesses. "Which steps did you guess at?" points you straight at the likely mistakes.
  • tentativeProps leak answers. In classroom pieces, background props and labels gave away the decisions students were meant to make.
  • confirmedLabel reconstructions. When a piece mixes real records (real titles, real data) with drawn stand-ins, say which parts are reconstructed.
  • tentativeBeauty can hide a missing explanation. One piece was judged "too pretty, under-explained".
  • tentativeHedge claims you can't check. Cultural and current-events claims get softer wording or a source on screen.
  • confirmedRead the video, don't watch it. An agent can't watch video efficiently: about 20 minutes of footage costs tens of millions of tokens as frames, and around ten thousand as a word-level transcript.
  • tentativeIf you can't start a fresh reviewer, hand it over. An agent working alone can't review its own video as if it were new.

Pitfalls that cost time here

  • A word count or quote is wrong
  • "Nothing changed" but the file is new
  • console.assert or console.table is missing

07 Make it legible 15 lessons · 2 pitfalls

Sizes, contrast and small honesty labels that decide whether the video works on a phone or at the back of a room.

  • confirmedText sizes. At 1080p: captions about 74 px, labels about 44 px.
  • confirmedContrast. At least 3:1 for lines and tracks against the background; coloured text needs a darker ink than the matching fill.
  • confirmedShow viewpoint changes. When switching from a flat diagram to a 3D or isometric view, show a small orientation card or animate the projection from flat to iso.
  • confirmedCause before effect. Draw the push before the motion, the input before the output.
  • confirmedLabel your cheats. "Sped up", "not to scale", "lines drawn thicker than real".
  • confirmedDate anything current. "As of March 2026" on any figure that can change.
  • tentativeA plain stand-in character. For "you could do this" pieces, a nondescript character with second-person captions ("you sand the edge") worked better than a named person.
  • tentativeBoth ends as strengths. In pieces about personality or learning styles, show each end of a scale as a strength, never one as the deficit.
  • tentativeMagnifier for detail. A close-up circle connected to its source by a cone reads better than cutting to a zoomed shot.
  • confirmedPush transitions need care. Sliding a whole scene sideways looks jittery unless offsets are whole pixels and a little motion blur is averaged in.
  • tentativeHand-drawn wobble at 4 fps. "Boiling" sketchy lines (redrawing them slightly differently) about four times a second reads as hand-drawn without being distracting.
  • tentativeMatching a reference clip. When remaking a real video, solve each shot's camera from the reference and key motion to its exact frames.
  • tentativeWord-synced captions. For a recorded talk, page captions one sentence at a time, at most 3 lines, at least 0.6 s per page, with the current word highlighted.
  • tentativeOne graphic per sentence, one color per idea. In an edit of a talk, give each sentence at most one graphic (diagram, chip, timeline, mock-up), keep one color per idea everywhere, and use 2 or 3 fonts.
  • tentativeCut-outs switch in with a wipe. Run background removal only on the frames where text passes behind the speaker or they leave their frame, and switch into the cut-out with a wipe so mask flicker doesn't show.

Pitfalls that cost time here

  • Text runs out of its panel when a window shrinks
  • Things move in steps instead of smoothly

08 Companion pages (optional) 2 lessons · 3 pitfalls

The same drawing code can power an interactive page next to the video.

  • confirmedReuse the video's code. The same renderAt(t) that renders the MP4 can power a web page with a scrubber, so readers can pause on any moment.
  • tentativeMake numbers draggable, with buttons. Inline numbers readers can change ("what if gravity were 12?") worked well with visible −/+ buttons; a dashed underline alone wasn't discoverable.

Pitfalls that cost time here

  • history.replaceState throws
  • Audio won't seek in a hosted page
  • The test browser won't play your MP4

07RUN

Run it yourself

The demos (tested)

Python 3 with numpy and skia-python, plus ffmpeg. On Ubuntu, skia needs the EGL library even for CPU rendering.

git clone https://github.com/lpcode808/animation-via-code.git
cd animation-via-code
sudo apt-get install -y libegl1 ffmpeg fonts-dejavu-core
python3 -m venv .venv && . .venv/bin/activate
pip install numpy skia-python
cd demos
python3 build.py bouncing_ball

Building writes over the shipped MP4 and contact sheet. Frames are cached in work/<name>; delete that folder after changing a scene's draw(), or the old frames are reused.

The template (browser)

Node 18+, Python 3 with numpy, and ffmpeg. Not yet run end to end in a browser; if a step fails, the demos are the tested version of the same idea.

cd template
npm install
npx playwright install --with-deps chromium
node render.mjs     # frames + cues.json
python3 audio.py    # audio.wav
bash mux.sh         # out.mp4, length checked
bash contact.sh     # contact.jpg
08NOTE

A caution on using these notes

Don't paste the whole guide into an agent's standing instructions.

When that was tried, every new video converged on the same pipeline and look. Give the agent the short prompt, and reach for the lessons when something breaks or you want to push past the default.
